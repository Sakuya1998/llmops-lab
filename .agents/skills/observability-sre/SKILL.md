# 可观测性与 SRE

## 工作流程

1. 确认服务边界、关键用户路径、依赖、流量模式和故障影响。
2. 从可用性、延迟、流量、错误和饱和度识别最重要的信号。
3. 先设计少量有明确用途的指标，再设计仪表盘和告警。
4. 给每条告警写清触发条件、持续时间、严重级别、用户影响、诊断步骤和恢复操作。
5. 提供可复现的验证方法，例如 PromQL 查询、模拟故障或规则检查。

## 指标规则

- 指标名称和标签保持稳定、含义清晰。
- 避免高基数标签：request ID、user ID、任意 URL、原始提示词、模型输出或任意错误文本。
- 不把敏感业务内容放进指标标签。
- 区分服务存活、服务就绪和业务依赖健康；一个简单的 liveness 端点不代表所有依赖都正常。
- 模型服务还应关注 TTFT、token 间延迟、吞吐量、并发、队列等待、GPU 利用率和显存，但必须确认对应指标真实可获取。
- 告警应尽量表达用户影响或持续故障，避免仅因瞬时抖动产生噪声。

## 故障排查

使用“症状 → 影响范围 → 指标/日志证据 → 假设 → 验证命令 → 缓解 → 根因 → 预防”的结构。不要在缺少证据时直接断言根因。

## 交付内容

至少给出：
- 指标清单及用途
- 关键 PromQL / 告警规则
- 仪表盘面板建议
- 告警验证方法
- 数据基数、隐私、存储和告警噪声风险
