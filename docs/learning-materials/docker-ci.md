# Docker 镜像与 CI 流水线

## 学习目标

理解从源代码到可部署镜像的基本交付链路，并建立可重复验证的 CI。建议用时 1–2 小时。

## 1. 构建链路

```text
Git commit
  -> 依赖安装
  -> 单元/API 测试
  -> 静态检查与格式检查
  -> 构建镜像
  -> 镜像扫描与标记
  -> 推送仓库
  -> 部署到目标环境
  -> 健康验证 / 回滚
```

并非每个项目都必须一开始具备全部阶段，但发布流程应逐步自动化，并且每一步有清晰失败条件。

## 2. 镜像可复现性

- 选择明确的基础镜像版本，并根据风险决定是否固定 digest。
- 依赖清单和锁定策略应与项目工具一致。
- 构建上下文只包含必要文件；使用 .dockerignore 避免复制虚拟环境、缓存、凭据和本地数据。
- 生产镜像优先采用非 root 用户、最小运行时依赖和明确入口。
- 镜像标签应能关联 Git commit 或版本，不要只依赖 latest。

固定版本提高可追踪性，但也需要定期升级修补漏洞；永远不升级并不安全。

## 3. CI 的价值

CI 将开发者机器上的手工步骤变成每次提交都能执行的验证。最低限度可包括：
1. 安装项目；
2. 运行测试；
3. Ruff 检查和格式验证；
4. mypy（按项目配置）；
5. 可选的构建验证。

CI 必须在真实运行后才能声称通过。工作流 YAML 存在不等于流水线已成功执行。

## 4. 缓存与安全

依赖缓存能加快流水线，但不能把缓存当作正确性证明。缓存键应覆盖依赖清单和运行时版本。CI 日志中避免输出密钥；第三方 Action 应审查来源、版本和权限范围。发布凭据使用最小权限，优先采用短期身份凭证而不是长期静态密钥。

## 5. 发布策略

- 滚动更新：逐步替换实例，需要正确的 readiness 和容量配置。
- 蓝绿发布：保留两套环境，切换流量，成本较高但回退直观。
- 金丝雀发布：先让小部分流量使用候选版本，基于指标逐步扩大。
- 回滚：不仅恢复镜像，还要考虑数据库迁移、配置变化和消息格式兼容性。

部署成功不代表业务成功。应验证启动、健康、关键 API、错误率和延迟。

## 实验

1. 检查仓库 Dockerfile 与 .dockerignore。
2. 本地构建镜像并确认实际启动命令。
3. 用非 root 身份运行，并验证文件权限。
4. 检查 CI workflow 是否覆盖测试和静态检查。
5. 为一次发布写出“成功条件、失败条件、回滚步骤”。

## 验收

- 能解释镜像层与构建缓存。
- 能说明 CI 测试通过与部署成功不是同一个结论。
- 能解释固定版本、镜像扫描和最小权限的意义。
- 能写出可执行的发布验证与回滚清单。
