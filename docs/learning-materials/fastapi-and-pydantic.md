# HTTP、FastAPI 与 Pydantic

> 目标：能从客户端请求一路追踪到服务端校验、处理和响应。建议用时 60–90 分钟。

## 1. 先理解一次 HTTP 请求

一次典型 API 请求可以抽象为：

```text
客户端
  -> DNS / TCP / TLS（取决于部署方式）
  -> HTTP 请求
  -> ASGI Server（例如 Uvicorn）
  -> FastAPI 路由匹配
  -> 请求数据校验（Pydantic）
  -> 业务逻辑
  -> HTTP 响应
  -> 客户端
```

在本地开发时，Uvicorn 负责接收连接并运行 ASGI 应用；FastAPI 提供路由、依赖注入、参数解析和 OpenAPI 文档等能力。Pydantic 负责按模型定义解析和校验数据。

生产环境通常还会有反向代理、负载均衡、认证、限流、超时和观测组件。不要把本地运行结构直接等同于完整生产架构。

## 2. HTTP 方法与状态码

| 方法/状态码 | 常见语义 | 注意点 |
|---|---|---|
| GET | 获取资源 | 通常不应改变服务端业务状态 |
| POST | 创建资源或执行动作 | 是否幂等取决于 API 语义与实现 |
| PUT | 整体替换资源 | 应定义资源不存在时的行为 |
| PATCH | 局部修改资源 | 应定义字段缺省与显式 null 的区别 |
| DELETE | 删除资源 | 成功时可返回 204，无响应体 |
| 200 | 成功并有响应内容 | 响应体结构应稳定 |
| 201 | 已创建 | 常用于创建资源 |
| 204 | 成功但无响应体 | 不要再返回 JSON 内容 |
| 400 | 请求本身不符合接口要求 | 具体使用规则应在 API 契约中统一 |
| 404 | 资源不存在或路由不存在 | 避免泄漏不该暴露的信息 |
| 422 | 请求数据校验失败 | FastAPI 默认常用于请求校验错误 |
| 500 | 未预期的服务端错误 | 不应把内部堆栈直接返回客户端 |

状态码的选择应与 API 契约一致。不要为了“让请求成功”而把所有错误都转换为 200。

## 3. Pydantic 模型的作用

请求模型不仅是类型提示，也是边界校验。示意：

```python
from pydantic import BaseModel, Field

class ModelCreate(BaseModel):
    name: str = Field(min_length=1, max_length=100)
    provider: str = Field(min_length=1, max_length=50)
    enabled: bool = True
```

它表达了：

- `name` 与 `provider` 必须提供字符串值；
- 字符串长度有明确边界；
- `enabled` 有默认值；
- 不符合模型约束的输入会在进入路由处理逻辑前被拒绝。

注意：类型转换和严格模式行为受 Pydantic 配置及版本影响；不要假设所有输入都只会被简单地“拒绝”或“接受”。可通过测试固定项目希望提供的行为。

## 4. 路由处理的职责边界

路由层适合做：

- 接收已经解析的请求参数；
- 调用清晰的业务函数；
- 把业务结果映射成 HTTP 响应；
- 声明必要的状态码和响应模型。

不要让路由函数同时承担大量业务规则、数据库访问、外部 HTTP 调用、重试和日志脱敏。随着复杂度增加，应将业务逻辑拆成可独立测试的函数或服务层。

## 5. 稳定的错误契约

客户端需要可预测的错误结构，例如：

```json
{
  "detail": "模型记录不存在"
}
```

这是示意，不代表仓库所有接口都已统一为该格式。设计错误契约时应明确：

- 哪些错误是用户可修复的输入问题；
- 哪些错误代表资源不存在或状态冲突；
- 哪些错误是服务端内部故障；
- 客户端可依赖哪些字段；
- 哪些内部信息绝不能返回，例如堆栈、数据库密码、内部令牌。

异常处理不能把所有异常都吞掉并返回成功。服务端应保留足够的内部诊断信息，但日志也必须避免记录凭据和敏感请求内容。

## 6. OpenAPI 与交互式文档

运行服务后访问：

`http://127.0.0.1:8000/docs`

FastAPI 通常会从路由声明、类型标注、Pydantic 模型和响应定义生成 OpenAPI 描述与交互式文档。文档是 API 契约的一部分，但它不会自动证明接口行为正确；测试仍然必不可少。

## 7. 动手任务

1. 阅读 `app/model_ops_api/main.py` 与 `schemas.py`。
2. 对每个路由写出：方法、路径、请求输入、成功响应、可能的错误。
3. 启动服务，分别发送一条合法请求和一条不合法请求。
4. 观察状态码与响应体，确认校验失败时业务处理是否执行。
5. 在不破坏现有接口的前提下，提出一个字段长度限制或响应模型改进，并为其写测试。
