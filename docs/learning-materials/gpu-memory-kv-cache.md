# GPU 显存、模型权重与 KV Cache

## 学习目标

学会用数量级估算判断模型能否加载，以及为什么并发和上下文长度会影响显存。估算用于规划，最终必须以实际运行和监控验证。

## 1. 模型权重的粗略估算

模型参数量为 P，平均每个参数使用 b bit 存储时，权重的理论存储量约为：

```text
权重字节数 ≈ P × b / 8
```

例如 7B 参数、16-bit 权重，粗略为 7×10^9×2 bytes，即约 14 GB（十进制）；实际显示的 GiB 会不同，且这还不包含运行时开销。

量化可降低每个参数的存储开销，但真实占用还受量化格式、scale/zero-point、部分高精度层、对齐和运行时实现影响。

## 2. 不止权重占用显存

总显存还要容纳 KV Cache、激活/临时张量、CUDA graph 或内核工作区、通信缓冲区和运行时开销。不同推理引擎的内存管理方式不同，因此不能简单把显存总量减去权重大小就当作精确可用容量。

## 3. KV Cache 为什么重要

自回归生成时，模型需要保存先前 token 的 Key/Value 状态，避免每生成一个新 token 都重算全部历史上下文。KV Cache 随活动序列的 token 数和并发序列数量增长。

简化理解：层数越多、KV heads 越多、head dimension 越大、缓存 token 越多，KV Cache 通常越大。具体计算需考虑模型架构、数据类型、张量并行和引擎实现。

## 4. 并发与上下文的权衡

同一张 GPU 上，更多并发请求通常意味着更多活动序列和 KV Cache；更长的上下文也会占用更多缓存。若显存预算不足，服务可能降低可接纳并发、发生 preemption/swap（取决于引擎配置）或直接 OOM。

因此容量规划至少要说明：
- 模型和权重格式；
- GPU 型号、显存和 GPU 数量；
- 最大上下文长度；
- 预期并发和输出长度；
- 量化方法；
- 服务引擎与版本；
- 预留安全余量和失败后的降载策略。

## 5. 观察什么指标

结合 GPU exporter、推理引擎指标和系统指标观察：
- GPU 显存已用/总量；
- GPU 利用率与功耗；
- 请求队列与活动序列数；
- KV Cache 使用率（若引擎暴露）；
- 请求错误、超时和排队延迟；
- 输出 token 吞吐量与 TTFT。

GPU 利用率低不一定表示服务没有瓶颈，也可能是 CPU/tokenization、网络、批处理、队列或显存限制造成的。

## 6. 容量实验

1. 记录硬件、驱动、CUDA、模型和引擎版本。
2. 从低并发开始，固定输入输出长度。
3. 逐步增加并发，每一步记录显存、吞吐量和 p95 延迟。
4. 另外改变上下文长度，比较 KV Cache 和延迟变化。
5. 设定停止条件，不要为了找到 OOM 边界而在共享或生产 GPU 上进行无保护压测。

## 验收

- 能估算不同精度下的权重存储量。
- 能说明为什么实际显存占用高于权重大小。
- 能解释 KV Cache 与上下文、并发的关系。
- 能给出一次可重复的容量实验记录模板。
