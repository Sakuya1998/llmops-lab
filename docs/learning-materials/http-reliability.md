# HTTP 服务可靠性：超时、重试、幂等与限流

## 学习目标

把运维中常见的超时、重试和流量保护思维应用到应用层。建议用时 1–2 小时。

## 1. 超时必须分层

一次请求可能经过客户端、负载均衡、反向代理、应用、数据库和模型服务。总超时应与各层超时相容，避免下游超时比上游长很多，导致调用方已放弃而后台工作仍占用资源。

区分连接超时、读取超时、整体请求 deadline 和业务任务期限。为外部调用设置明确超时，不要无限等待。超时不是取消保证：下游可能已经执行了操作，只是响应未及时返回。

## 2. 重试不是免费恢复

重试适合有限的、可恢复的失败，例如部分临时网络错误；不适合无条件重试所有 4xx、验证错误或昂贵操作。

重试策略至少应定义：
- 最大尝试次数；
- 总时间预算；
- 指数退避与随机抖动；
- 哪些错误可重试；
- 是否存在幂等保证；
- 重试造成的额外负载上限。

如果多个层级都重试，尝试次数会相乘。例如客户端 3 次、网关 3 次、服务 3 次，最坏可能放大为 27 次下游尝试。

## 3. 幂等

幂等意味着对同一逻辑操作重复执行，不会产生额外的业务副作用。HTTP 方法的语义不能替代实际实现保证。

对于创建任务、扣费、提交推理任务等写操作，可考虑 Idempotency-Key。服务端需要定义键的作用域、保存期限、请求体一致性检查、并发重复请求行为和结果回放策略。仅仅接收一个请求头并不能自动实现幂等。

## 4. 限流与并发控制

限流控制一段时间内允许的请求速率；并发限制控制同时在执行的工作数量。两者不同。模型推理还需要考虑输入 token 数、输出 token 上限、队列长度、GPU 显存和请求成本，而不只是 QPS。

被拒绝的请求应得到明确且稳定的响应，并可通过指标观察拒绝率。限流器本身也有状态一致性和多副本问题。

## 5. 背压与队列

当消费者处理速度低于请求进入速度时，队列持续增长会增加延迟和内存压力。系统应设置队列上限、排队超时和拒绝策略，避免把所有请求无限积压。异步任务还要定义任务状态、取消、重试、死信和结果保留策略。

## 6. 可靠性实验

在本地测试环境中：
1. 为一个外部请求设置合理超时。
2. 模拟下游超时，观察错误映射和日志。
3. 为重试增加最大次数与退避，并确认不会无限循环。
4. 对写接口重复发送相同操作，验证实际副作用。
5. 观察并发升高时延迟、错误率和队列长度的变化。

不要对真实付费 API 或生产服务进行故障注入，除非明确授权并做好回滚方案。

## 验收

- 能区分连接超时、读取超时与整体 deadline。
- 能解释为什么超时后重试可能重复执行操作。
- 能说明幂等键的服务端实现要求。
- 能解释限流、并发控制与队列上限的区别。
