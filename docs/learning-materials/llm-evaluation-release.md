# LLM 评测、回归测试与发布门禁

## 学习目标

建立可重复的评测流程，能够比较提示词、模型和参数变更，并用质量、延迟、成本和安全指标共同决定是否发布。

## 1. 为什么需要评测

LLM 输出可能具有随机性，传统的“测试结果必须逐字相同”通常不够适用。但这不意味着可以只靠人工感受判断。应将业务目标拆成可观察、可重复的评测维度，并记录评测数据和版本。

## 2. 数据集设计

一个评测样本通常包含输入、预期特征或参考答案、任务类型、标签和数据来源。要覆盖：
- 常见正常请求；
- 边界输入和格式错误；
- 长上下文；
- 多语言或不同任务类型；
- 安全拒绝与提示注入测试；
- 已知线上问题的脱敏复现样本。

数据集应有版本、访问权限和保留策略。禁止把真实用户敏感内容直接复制到公开仓库。优先使用合成或已授权且脱敏的数据。

## 3. 评测维度

按任务选择指标：
- 正确性/事实一致性；
- 指令遵循和格式有效性；
- 相关性、完整性和可读性；
- 安全性与拒绝行为；
- TTFT、总延迟和吞吐量；
- token 使用量和估算成本。

单一分数可能掩盖重要退化。例如平均质量提高，但安全违规率上升，不能直接判定为可发布。

## 4. 基线与候选版本

每次评测应记录：
- 模型 ID / revision；
- prompt 模板版本；
- 推理参数；
- 评测代码 commit；
- 数据集版本；
- 随机种子（若支持）；
- 执行环境和时间；
- 指标定义和结果。

先运行基线，再对候选版本使用相同数据和规则比较。若模型服务或评测器本身变化，应在报告中注明。

## 5. 自动评测与人工评审

精确匹配适合格式或确定性任务；分类任务可用准确率、精确率、召回率等；生成任务可能需要规则、参考答案指标、模型裁判和人工评审组合。

模型裁判也会有偏差、对提示词敏感、版本变化和自我偏好问题。关键发布决策不应完全依赖单一 LLM-as-a-judge 分数。对人工评审，应尽量采用明确 rubric、盲评和分歧复核。

## 6. 发布门禁

一个简单门禁可以检查：
- 必要样本是否全部执行；
- 格式有效率是否达到最低要求；
- 关键质量指标是否未显著退化；
- 安全违规是否超过阈值；
- 延迟和成本是否仍在预算内。

阈值应由业务风险与基线数据决定，而不是从示例直接照搬。小样本结果存在统计不确定性，需要标注样本量和置信度，不能过度解读微小差异。

## 7. 实验

1. 创建一组不含敏感数据的合成样本。
2. 版本化保存 prompt、模型参数和评测规则。
3. 运行基线和候选版本，输出机器可读 JSON/CSV 结果。
4. 比较质量、错误率、延迟与 token 成本。
5. 故意让候选版本违反一个门禁，验证流水线会失败并输出原因。

## 验收

- 能解释评测集、基线、候选版本和门禁的关系。
- 能说明模型裁判的局限。
- 能保证评测报告可追溯到代码、模型、提示词和数据集版本。
- 能用自动化规则阻止明显退化的候选版本。
