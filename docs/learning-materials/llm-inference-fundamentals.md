# 大语言模型推理基础

## 学习目标

理解一次 LLM 请求如何从文本变成 token、经过模型计算，再返回生成文本；能读懂延迟、吞吐量、上下文长度和 token 等基本概念。建议用时 1–2 小时。

## 1. 训练与推理

训练通过大量样本调整模型参数；推理使用已经训练好的参数对输入生成输出。模型服务工程通常关心推理成本、延迟、吞吐量、质量、可用性和数据安全。

## 2. Token 与上下文窗口

模型通常处理 token，而不是直接按字符计数。一个 token 可能对应一个词的一部分、标点或其他文本片段。不同 tokenizer 对同一段文字的切分不同，因此字符数不能精确代表 token 数。

上下文窗口限制一次请求中模型可处理的输入和生成内容总量，具体计数规则取决于模型。请求超长时，服务可能拒绝、截断或采用其他策略，必须明确行为。

## 3. 自回归生成

常见 decoder-only LLM 逐 token 生成：先对输入进行 prefill，再逐步 decode 新 token，直到达到停止条件或输出上限。

- Prefill：处理输入上下文，计算成本与输入长度强相关。
- Decode：逐步生成输出，通常每一步都依赖前一步结果。
- TTFT：从请求开始到首个输出 token 到达的时间。
- TPOT：相邻输出 token 之间的平均生成时间（不同工具可能采用略有差异的定义）。
- E2E latency：整个请求从开始到完成的耗时。

流式输出可以让用户更早看到首个 token，但不代表整个响应完成得更快。

## 4. 延迟与吞吐量

吞吐量可能指请求/秒、输入 token/秒或输出 token/秒。报告基准数据时必须写清楚口径、并发、输入输出长度、模型、硬件、量化方式、软件版本和采样方法。

平均值会掩盖长尾。应同时观察 p50、p95、p99 延迟、错误率和超时率。

## 5. 生成参数

常见参数包括 max tokens、temperature、top-p、停止条件等。参数影响输出长度、随机性、质量和成本。参数名和默认值应以具体服务/API 版本为准。max output tokens 是成本和延迟保护的重要上限之一，但不能替代请求体大小限制和并发控制。

## 6. 模型服务的失败模式

- 输入超过上下文限制；
- 请求输出过长或消耗预算；
- 模型加载失败、权重不兼容；
- GPU 显存不足；
- 队列堆积导致长尾延迟；
- 客户端断开后计算仍继续；
- 模型/Tokenizer/提示词版本不一致；
- 返回格式不符合下游要求。

可靠服务需要对这些情况定义可观察、可恢复的处理策略。

## 7. 实验

1. 选一段中文和一段英文，使用可用 tokenizer 统计 token 数，比较字符数与 token 数。
2. 设计短输入/长输入、短输出/长输出四组请求。
3. 说明每组请求可能怎样影响 prefill、decode、TTFT 和总耗时。
4. 阅读仓库 vLLM 示例，标记模型名、最大上下文、并发和输出长度限制。
5. 没有 GPU 时，用文档和 CPU 上的小型模型做概念实验即可，不要为了完成课程盲目租用昂贵 GPU。

## 验收

- 能解释 token、上下文窗口、prefill 和 decode。
- 能区分 TTFT、TPOT、总延迟与吞吐量。
- 能解释为什么基准测试必须说明并发与 token 长度。
- 能列举至少四种推理服务失败模式。
