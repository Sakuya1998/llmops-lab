# Python 服务工程化：从脚本到可维护服务

## 学习目标

把熟悉的 Python 自动化脚本提升为可安装、可测试、可配置、可观测、可部署的服务。建议分 3–5 次、每次 60–120 分钟学习。

## 1. 脚本与服务的差别

脚本通常由人主动运行，失败后人工重试；服务长期运行，持续接收不可信输入，并且可能同时处理多个请求。因此服务必须明确生命周期、输入契约、错误语义、并发边界、配置来源、日志和退出行为。

从运维角度理解：
- 脚本参数类似一次性命令行参数；HTTP 请求是持续变化的外部输入。
- 退出码类似一次任务结果；HTTP 状态码是每个请求的结果。
- 标准输出适合临时观察；结构化日志要便于检索和关联。
- 定时重跑脚本不等于安全重试请求；写操作可能重复产生副作用。

## 2. 推荐分层

```text
HTTP / CLI 入口
    -> 输入解析与校验
    -> 应用服务（编排用例）
    -> 领域规则
    -> Repository / 外部依赖适配器
```

不需要一开始就引入复杂的 Clean Architecture 框架。分层的目的，是让业务规则不被 HTTP、数据库或某个云厂商 SDK 锁死，并让测试能独立验证关键行为。

## 3. 类型标注与数据模型

类型标注让 IDE、静态检查和读代码的人更容易发现误用，但 Python 默认不会在运行时强制执行所有注解。外部输入仍应通过 Pydantic 等边界校验工具验证。

区分：
- API schema：外部请求/响应契约。
- Domain model：内部业务概念与规则。
- Persistence model：数据库存储结构。

小项目可以复用部分模型，但不要默认三者永远相同。API 字段变更、数据库迁移和领域规则的生命周期不同。

## 4. 配置与环境

配置应在启动时集中读取并校验，例如监听地址、端口、日志级别和外部服务地址。敏感值通过环境变量或受控密钥管理系统注入，不写入 Git，不在日志中打印完整配置对象。

建议明确配置优先级，例如：默认值 < 配置文件 < 环境变量。不要在业务函数中到处读取环境变量，否则测试和行为推理会更困难。

## 5. 错误处理

区分三类错误：
1. 可预期的业务错误，例如资源不存在；
2. 可恢复的依赖错误，例如暂时超时；
3. 未预期的程序错误，例如违反不变量。

入口层负责将错误映射为稳定的外部响应；内部日志保留诊断上下文但避免秘密和敏感内容。不要无差别捕获所有异常后返回成功，也不要将堆栈暴露给调用者。

## 6. 并发与共享状态

Web 服务通常会同时处理多个请求。全局可变字典、可变单例和缓存必须明确线程/协程安全性、数据一致性及多副本语义。进程内锁只能协调同一进程，不能替代跨副本的数据库事务或分布式协调。

## 7. 代码质量工具

- pytest：验证行为。
- Ruff：检查常见错误与风格问题，也可格式化代码。
- mypy：根据配置检查类型使用。
- Git diff：检查本次变更是否超出任务范围。

工具发现问题后，应先理解错误，再修复根因。不要把忽略规则当成首选方案。

## 8. 实验

1. 选择一个 API 路由，画出请求到响应的调用链。
2. 将一段业务判断提取成独立函数并编写单元测试。
3. 将一项硬编码配置移至集中配置模块。
4. 为一个预期业务错误定义稳定响应。
5. 运行测试和静态检查，并记录实际结果。

## 验收

- 能画出当前项目的调用链和依赖方向。
- 能说明 API schema、领域模型和数据库模型为何可能不同。
- 能区分业务错误、依赖错误与程序错误。
- 能说明进程内共享状态在多副本下的局限。
