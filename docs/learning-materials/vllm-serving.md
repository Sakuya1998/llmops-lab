# vLLM 模型服务与运维

## 学习目标

理解 vLLM 的作用、启动参数、健康验证和基准测试流程。实际命令需结合模型许可、硬件、vLLM 版本和资源预算验证。

## 1. vLLM 解决什么问题

vLLM 是面向 LLM 推理的服务与执行引擎之一，提供 OpenAI 兼容 API（具体端点和支持能力依版本而异），并通过调度、连续批处理和 KV Cache 管理等技术提高 GPU 推理效率。

它不是模型训练框架，也不会自动解决身份认证、租户隔离、配额、数据治理和生产发布等全部问题。

## 2. 启动前检查

先确认：
- 模型仓库许可允许当前使用方式；
- GPU 型号、驱动、CUDA 兼容性和可用显存；
- 模型格式、架构、Tokenizer 是否受当前版本支持；
- 权重来源和校验策略；
- 预期上下文、并发、输入/输出 token 上限；
- 模型下载和缓存磁盘空间；
- 服务是否会暴露到不可信网络。

不要将带有敏感权限的 Hugging Face Token 写进命令历史或镜像层。优先通过安全的环境注入方式传递凭据。

## 3. 本地实验命令示意

以下只是命令形态示例；模型名称、参数和显存需求必须按实际环境调整，不能视为在任意机器可直接成功运行的生产配置。

```bash
vllm serve <允许使用的模型ID或本地模型路径> \
  --host 127.0.0.1 \
  --port 8000 \
  --max-model-len <经过容量评估的上下文长度>
```

在没有身份认证和网络隔离的实验环境中，优先绑定回环地址。不要为了方便把未经保护的推理 API 直接绑定到公网地址。

## 4. 验证服务

服务启动后，先查看进程日志、模型加载结果和显存占用，再调用当前版本文档支持的健康端点与推理端点。记录：
- 进程是否持续运行；
- 模型是否真正加载完成；
- 一条最小请求能否成功；
- 返回是否包含预期字段；
- 无效模型名、超长输入和超时的表现。

HTTP 端口打开并不意味着模型已经可推理；容器 Running 也不等于业务就绪。

## 5. 性能测试设计

至少固定并记录：
- GPU 型号与数量；
- 驱动、CUDA、vLLM 和模型版本；
- 模型精度/量化；
- 输入 token 长度、输出 token 上限；
- 并发、请求数和预热方式；
- 测试持续时间；
- TTFT、总延迟、输出 token/s、错误率和显存峰值。

先建立低并发基线，再逐步提高并发。避免在没有上限的情况下发起并发压测。

## 6. 生产化前的缺口

通常还需要网关或身份认证、租户配额、并发/队列限制、TLS、网络策略、审计日志、模型许可管理、指标采集、容量告警、滚动升级和回滚方案。具体能力取决于部署方式，不要假设 vLLM 单独承担这些职责。
